# 12. Магнитофон: `EMT 36` и формат файла на ленте

> **Источники главы**
> * **[РСП § 9]** «Обмен с магнитной лентой» (с. 45–49) — нормативное описание `EMT 36`,
>   блока параметров и протокола поиска файла.
> * **[З]** «Операторы прерывания» (описание `EMT 36` и формата файла на МЛ),
>   «Системная область» (ячейки драйвера магнитофона 300…316),
>   «Концепция системных драйверов» (перехват `EMT 36`).
> * **[Рад]** — Л. И. Радченко, «БК-0010 и магнитофон» (НПК «СБИС», 1990, 40 с.):
>   комментированный дизассемблер драйвера, детальный формат сигнала,
>   защита и регенерация программ. **Главный источник по формату и драйверу.**
> * **[МПСС]** (вторичный) — параметры накопителя.
> * **[ЭМ]** `bkemu-QT/devemu/Tape.cpp` — длительности импульсов, структура файла.

Внешняя память БК-0010-01 — бытовой кассетный магнитофон (штатно — «Электроника 302»),
подключаемый через разъём «МАГНИТОФОН». Носитель — стандартная компакт-кассета типа **МК60**.

| Параметр | Значение |
| --- | --- |
| Скорость обмена | **1200 бод** |
| Метод записи | разновидность широтно-импульсной модуляции |
| Плотность записи | ≈25 бит/мм |
| Ёмкость кассеты МК60 | **до 500 Кбайт** [РСП], [Рад] (статья разработчиков 1985 г. называет 256 Кбайт — см. §16.5, Г5) |

Контроллер накопителя построен по принципу программно-аппаратного управления: аппаратно
реализованы лишь регистр временного хранения и схема преобразователей уровня, все основные
функции выполняются программой драйвера.

Всё взаимодействие идёт через командное прерывание **`EMT 36`** — самое сложное
из EMT-функций БК. Обработчик расположен в ПЗУ по адресу **116076** [✓ ПЗУ].

## 12.1. Вызов `EMT 36`

| Вход | |
| --- | --- |
| `R1` | **Адрес блока параметров** |

Блок параметров может располагаться с любого чётного адреса ОЗУ, но в системной области
под него зарезервирована зона **320…371**. Именно её используют Фокал, Бейсик, ПМ и МСД.

## 12.2. Блок параметров

| Смещение | Адрес (штатный) | Размер | Мнемоника DMBK | Содержимое |
| --- | --- | --- | --- | --- |
| 0 | **320** | байт | `KOM` | **Команда** |
| 1 | **321** | байт | `OTWET` | **Ответ** (код завершения) |
| 2 | **322** | слово | `ADRMAS` | Адрес массива на запись или чтение |
| 4 | **324** | слово | `DLMAS` | Длина массива на запись (при чтении нужно обнулять) |
| 6 | **326…345** | 20 (16д) байт | `IMMAS` | Имя массива на запись или чтение |
| 26 | **346** | слово | `ADRTM` | Адрес **текущего** массива |
| 30 | **350** | слово | `DLTMAS` | Длина текущего массива |
| 32 | **352…371** | 20 (16д) байт | `IMTMAS` | Имя текущего массива |

Полный размер блока — **52** (октально) = **42** байта.

> **О нумерации байтов.** В [Рад] смещения даны **восьмеричными** («6–25» — имя,
> «32–51» — имя текущего массива), в [РСП] те же поля описаны с **десятичными**
> номерами («6–21», «26–41»). Числа разные, поля одни и те же
> (см. §16.5, А6).

**Текущим** называется массив (файл), имя которого прочитано последним, независимо от
того, загружался ли он в ОЗУ. Поля 346/350/352 заполняются при любом чтении, включая
фиктивное, — это позволяет узнать параметры файла, не загружая его.

### Байт «команда» (320)

| Значение | Операция |
| --- | --- |
| 0 | Останов двигателя магнитофона |
| 1 | Пуск двигателя магнитофона |
| 2 | **Запись** файла на МЛ |
| 3 | **Чтение** файла с МЛ |
| 4 | **Фиктивное чтение** (поиск / просмотр кассеты) |

При командах 2, 3, 4 двигатель включается и выключается автоматически — отдельно
подавать 0 и 1 не требуется.

> Команды 0 и 1 нужны только при магнитофоне с дистанционным управлением: после завершения
> операции БК выключает двигатель, и ленту становится невозможно даже перемотать — ДУ
> блокирует запуск с клавиш магнитофона. Для ручной перемотки нужно либо отстыковать
> штекер ДУ, либо заранее предусмотреть в программе команды 1/0 (аналог директив
> `МП`/`МС` в МСТД).

### Байт «ответ» (321)

| Значение | Смысл |
| --- | --- |
| 0 | Операция завершена без ошибок |
| 1 | Имя файла на МЛ не совпадает с заданным |
| 2 | Ошибка контрольной суммы |
| 4 | Останов по клавише «СТОП» |

Ячейка `301` дублирует байт ответа и является по отношению к нему **первичной**:
драйвер работает с `301`, а в байт `321` значение копируется только в конце
(`116236 MOVB 301,1(R1)`) [✓ ПЗУ].

### Протокол поиска файла [РСП § 9]

При чтении (команда 3) драйвер сравнивает прочитанное с ленты имя с заданным. Если имена
**не совпали**, драйвер:

1. записывает в байт ответа значение 1;
2. возвращает управление вызвавшей программе;
3. **двигатель магнитофона при этом не останавливает**.

Благодаря этому программа может **повторно передать управление драйверу, не изменяя блок
параметров**, и поиск нужного файла продолжится с того же места ленты. Именно на этом
построены все каталогизаторы и загрузчики многофайловых программ.

Останов двигателя производится по завершении операции (успешном или по «СТОП»), а также
явной командой 0.

### После успешной загрузки

Адрес загрузки и длина массива записываются также в ячейки **264** и **266**.
Если при загрузке задать адрес 0, файл будет загружен по адресу, указанному в его
оглавлении на ленте.

Контрольная сумма файла помещается в ячейку **312**. Она вычисляется **не так**, как
контрольная сумма по директиве `Х` МСД, и обычно с ней не совпадает.

## 12.3. Пример: запись файла на МЛ

Диалоговая программа: спрашивает адрес, длину и имя, затем записывает файл.

```asm
; Запись файла на МЛ с помощью EMT 36
BEG:    MOV     #346,R3             ; конец имени файла
0:      MOVB    #40,-(R3)           ; очистка имени файла — пробелы
        CMP     #320,R3             ; во все байты
        BNE     0                   ; до R3 = 320
        MOV     #2,(R3)+            ; команда «запись»; R3 = 322
        MOV     'A=',R0             ; запрос «АДРЕС=»
        CALL    INP                 ; ввод адреса; R3 = 324
        MOV     'Д=',R0             ; запрос «ДЛИНА=»
        CALL    INP                 ; ввод длины; R3 = 326
        MOV     'И=',R0             ; запрос «ИМЯ=»
        EMT     16                  ; выдача
        SWAB    R0                  ; запроса
        EMT     16                  ; на экран
        MOV     #5020,R2            ; ограничители: «ВВОД» или длина 16д
        MOV     R3,R1               ; адрес имени — 326
        EMT     10                  ; ввод имени
        MOVB    #40,-(R1)           ; заменить код 12 на пробел
        MOV     #320,R1             ; адрес блока параметров
        EMT     36                  ; выполнить запись файла
        EMT     6                   ; ожидание нажатия клавиши
        BR      BEG

; Выдача запроса и ввод числовых данных
INP:    EMT     16                  ; первый символ запроса
        SWAB    R0
        EMT     16                  ; второй символ
        CALL    @#100472            ; п/п ПЗУ: ввод восьмеричного числа в R5
        MOV     R5,(R3)+            ; число — в блок параметров
        MOV     #12,R0              ; перевод
        EMT     16                  ; строки
        RET
        END
```

Использована подпрограмма ПЗУ **`@#100472`** — ввод восьмеричного числа с клавиатуры
с возвратом результата в `R5` [✓ ПЗУ]. Это избавляет от размещения аналогичной довольно
длинной подпрограммы в ОЗУ.

## 12.4. Формат файла на магнитной ленте

> Раздел переработан по книге **[Рад]** — Л. И. Радченко, «БК-0010 и магнитофон»
> (НПК «СБИС», 1990, 40 с.). Это единственный источник, описывающий формат
> с точностью до отдельных элементов сигнала; [РСП § 9] и [З] дают его укрупнённо.

### Элементы сигнала

Каждый элемент при передаче на магнитофон преобразуется в **два импульса одинаковой
длины, но разной полярности** — используется широтно-импульсная модуляция.
Длительности (L — длительность самого короткого элемента):

| Элемент | Длительность |
| --- | --- |
| Логический нуль и **синхроэлемент** | **L** |
| Логическая единица | **2L** |
| **Выходной маркер** | **4L** |
| **Входной маркер** | **8L** (вдвое шире выходного) |

При чтении компьютер измеряет длительность импульсов. Нуль от единицы отличается
сравнением с **пороговым значением, в полтора раза большим длительности логического
нуля**: меньше порога — нуль, иначе — единица. Измеренный порог заносится в ячейку
**`314`**.

[✓ Совпадает с реализацией [ЭМ] `bkemu-QT/devemu/Tape.cpp`, функция `DefineLength`:
1 → «0» и синхроимпульс, 2 → «1», 4 → маркер, 8 → очень длинный импульс.]

### Структура файла

Файл состоит из **семи** частей:

```
┌────────────────────────────────────┐
│ 1. Входная настроечная             │  входной маркер (в несколько раз длиннее
│    последовательность              │  выходного) + 10000 синхроэлементов
├────────────────────────────────────┤
│ 2. Настроечная последовательность  │  входной маркер длительностью
│    заглавия                        │  с синхроэлемент
├────────────────────────────────────┤
│ 3. Заглавие файла                  │  слово адреса загрузки,
│                                    │  слово длины, 20 байт имени
├────────────────────────────────────┤
│ 4. Настроечная последовательность  │
│    массива                         │
├────────────────────────────────────┤
│ 5. Массив (тело файла)             │
├────────────────────────────────────┤
│ 6. Контрольная сумма массива       │  одно слово
├────────────────────────────────────┤
│ 7. Выходная настроечная            │  400 синхроэлементов; входной маркер
│    последовательность              │  более чем вдвое длиннее выходного
└────────────────────────────────────┘
```

**Настроечная последовательность** в общем виде — это входной маркер, некоторое число
синхроимпульсов, выходной маркер, логическая единица и синхроэлемент.

Назначение каждой:

| Последовательность | Для чего |
| --- | --- |
| **Входная** | Определение начала файла, **измерение порогового значения**, синхронизация |
| **Заглавия** и **массива** | Задержка перед передачей соответствующей части и синхронизация. Задержка нужна, чтобы машина успела решить, тот ли файл найден |
| **Выходная** | Завершить чтение файла, если произошёл сбой синхронизации |

Заглавие, массив и контрольная сумма — последовательности логических единиц и нулей,
**перемежаемых синхроэлементами**.

> **Три пары «маркер + настроечная последовательность»** — ровно это ищет эмулятор:
> в `Tape.cpp` подряд идут `FindMarker1()` → `FindTuning(7, marker1)` →
> `FindMarker()` → `FindTuning(7, marker2)` → `FindMarker()`.

### Блочная запись

При **блочной записи** — например, при сохранении программ на Бейсике — файл разбивается
на блоки, и **каждый блок записывается в описанном формате целиком**.

### Определение фазы

Полярность выхода у разных магнитофонов различается. Фаза определяется по маркеру
и фиксируется в ячейке **`300`**: 0 — прямой сигнал, 377 — инверсный.

### Контрольная сумма

* КС на ленте — **сумма всех байтов файла с учётом битов переноса**.
* При вычислении КС загруженного массива **не учитываются** настроечные
  последовательности, маркеры, заглавие и сама КС.

> Известный дефект: иногда БК воспринимает все считываемые биты как нулевые, включая
> записанное значение КС. Ошибка чтения очевидна визуально, но машина считает операцию
> успешной (КС пустого массива равна нулю при любой длине).

## 12.4а. Формат файла `.bin`

Файл `.bin` — де-факто стандарт хранения БК-программ на современных носителях и в
эмуляторах. Он представляет собой **оглавление файла с ленты плюс тело**, без УсП,
маркера и контрольной суммы:

```
слово 0 (байты 0–1) — адрес загрузки
слово 1 (байты 2–3) — длина массива в байтах
далее               — тело файла (<длина> байт)
```

Формат порождён форматом оглавления на МЛ (§11.4) и потому напрямую совместим
с загрузкой через `EMT 36`.

Подтверждение — документация кросс-ассемблера БКТурбо8
(`GID-src/BKemu/Docs/BKTurbo8.html`): «Генерируется `.bin` файл, у которого первым словом
идёт адрес загрузки, вторым — размер файла, совместимый с эмуляторами». Там же упомянут
вариант `.raw` — то же тело без заголовка.

Максимальная длина получаемой программы в БКТурбо8 — `0177000` байт.

## 12.5. Имя файла

До **16д (20 восьм.) любых символов**. Если имя короче, оно автоматически дополняется
пробелами (код 40). При вводе имени через `EMT 10` с ограничителем «ВВОД» последний
введённый байт (код 12) нужно заменить пробелом — см. пример выше.

## 12.6. Магнитофон и дисковые ОС

Практически во всех дисковых ОС для БК (NORD, ANDOS и др.) реализована **автоматическая
переадресация чтения-записи по `EMT 36` на диск**: EMT-прерывание перехватывается,
и функция `EMT 36` подменяется её «дисковой» версией. Это обеспечивает работу с диском
большинства старых программ, рассчитанных на магнитофон.

Два важных практических вывода:

1. **Ввод-вывод файлов в прикладных программах нужно делать стандартным способом —
   через `EMT 36`**, а не прямым обращением к «магнитофонным» подпрограммам монитора
   (кроме особых случаев, когда программа рассчитана только на магнитную ленту).
2. При адаптации многофайловых программ к диску подгрузку частей тоже следует делать
   **только через `EMT 36`**. Попытки писать собственные загрузчики, работающие
   напрямую с каталогом имён и секторами, приводят к тому, что программа работает
   лишь в одной ОС, и кому-то придётся «взламывать» её и делать адаптацию заново.

Тем же путём — перехватом `EMT 36` — реализуются нестандартные форматы записи на МЛ.
Автор книги описывает драйвер, работающий на **4000 бод** вместо стандартных 1200,
совместимый со всеми программами, которые пользуются штатным `EMT 36`.

Аналогично можно организовать обмен с квазидиском на дополнительном ОЗУ и даже вывод
на принтер тех блоков, которые программа собиралась записать на ленту.

## 12.6а. Размер драйвера и размещение в ПЗУ

Штатный драйвер `EMT 36` занимает в ПЗУ монитора **около 1700 байт** [КП, `kpss7`] —
это заметная доля восьмикилобайтной МДС и одна из причин, по которой альтернативные
драйверы магнитофона (спецформаты, ускоренная запись) писались компактнее и грузились
в ОЗУ поверх штатного через перехват вектора `@#30`.

Программы, рассчитанные на постоянное присутствие в машине, прошивали
в **ППЗУ КМ1801РР1** (электрическое стирание, по подключению идентично К1801РЕ2),
размещая их в адресах **120000…177600** — то есть вместо штатных ПЗУ Бейсика
(см. [15-схемотехника-и-доработки.md](15-схемотехника-и-доработки.md), §15.4
о выключателях ПЗУ).

## 12.6б. Драйвер изнутри

Книга [Рад] содержит **полный комментированный дизассемблер** штатного драйвера
магнитофона. Ниже — его опорные точки; полный листинг см. в самой книге.

| Адрес | Что здесь |
| --- | --- |
| **`116076`** | **Начало драйвера магнитофона:** `JSR R4,110346` — сохранение R0–R4 в стеке подпрограммой монитора |
| `110346` / `110362` | Подпрограммы сохранения и восстановления регистров (см. [09-монитор.md](09-монитор.md), §9.6) |
| `116214` | Собственный обработчик вектора 4, устанавливаемый драйвером на время работы |
| `116256` | Запись массива на ленту |
| `116640` | Чтение массива с ленты |
| `117070` | Подпрограмма измерения длительности импульса (определение фазы) |

### Пролог и эпилог: комментированный дизассемблер [✓ ПЗУ]

Восстановлено дизассемблированием `bk10_017_mon.rom` в эмуляторе-отладчике
`bk0010-emulator` (см. §16.4).

```
116076  JSR   R4, 110346      ; сохранить R0–R4
116102  MOV   R1, 306         ; ABP := адрес блока параметров
116106  MOV   #177716, R3     ; R3 → системный регистр
116112  CLR   300             ; сбросить флаг фазы
116116  CLR   302             ; PRFCT := 0 — чтение не фиктивное
116122  MOV   @#4, -(SP)      ; сохранить прежний вектор 4 в стеке
116126  MOV   #116214, @#4    ; подставить свой обработчик зависания
116134  MOV   SP, 310         ; BUFSP := SP — точка возврата при сбое
116140  MOVB  (R1), R0        ; R0 := байт команды из блока параметров
        ...                   ; разбор команды 0/1/2/3 и переход
116214  MOV   310, SP         ; ← сюда попадаем по вектору 4: восстановить стек
116220  MOVB  #4, 301         ; код ошибки 4
116226  MOV   #220, (R3)      ; остановить двигатель магнитофона
116232  MOV   306, R1         ; вернуть адрес блока параметров
116236  MOVB  301, 1(R1)      ; 301 → байт «Ответ» (321)
116244  MOV   (SP)+, @#4      ; вернуть прежний вектор 4
116250  JSR   R4, 110362      ; восстановить R0–R4
116254  RTS   PC
```

Три вывода, которых нет ни в одном текстовом источнике:

1. **Драйвер подменяет вектор 4 на всё время работы.** Прежнее значение он кладёт
   в стек и возвращает на выходе. Поэтому любое зависание во время обмена с лентой
   (нечётный адрес, обращение к несуществующей памяти, клавиша «СТОП») не роняет
   машину, а даёт аккуратный выход с **кодом ответа 4**. Это же объясняет, почему
   приёмы защиты через вектор 4 (§12.6в) действуют только **вне** работы драйвера.
2. **Ячейка `310` (`BUFSP`) — не просто буфер, а точка возврата в стиле «longjmp»:**
   `MOV SP,310` на входе и `MOV 310,SP` в обработчике сбоя. Именно поэтому драйверу
   важно, сколько данных программа держит под вершиной стека.
3. **Байт «Ответ» заполняется один раз, в самом конце.** Пока драйвер работает,
   актуальное состояние лежит в `301`, а не в `321`.

> **Именно этот пролог перехватывают внешние контроллеры.** В прошивке контроллера
> Gryphon-MPI лежит изменённая копия ПЗУ 1801РЕ2-017, отличающаяся от штатного
> ровно на 27 байт, и все они приходятся на диапазон **`116102`–`116135`** — то
> есть на приведённый выше пролог. Вместо подготовки к работе с лентой туда
> вписан короткий обмен с контроллером, после которого управление возвращается
> через ту же штатную подпрограмму `110362`; вход `116076` с сохранением
> регистров не тронут. Так «чтение с кассеты» превращается в чтение с SD-карты.
> Разбор — в [18-Gryphon-MPI.md](18-Gryphon-MPI.md), §18.5.

Коды, записываемые в `301` [✓ ПЗУ]: **2** — несовпадение контрольной суммы
(`117250`, сразу после сложения слов массива), **4** — срабатывание вектора 4
(`116220`).

> **Взаимная проверка.** Адрес `116076` совпадает с тем, что даёт таблица обработчиков
> `EMT`, восстановленная **дизассемблированием ПЗУ** (`EMT 36` → `116076`,
> см. [09-монитор.md](09-монитор.md), §9.4). Печатный источник 1990 года и содержимое
> ПЗУ подтверждают друг друга независимо — как и точка входа `110346`.

**Использование стека.** Драйвер может сохранять в стеке **до семи значений, суммарно
не более 16 байт**. Это надо учитывать программам, которые размещают свои данные
непосредственно под вершиной стека.

Ячейки системной области, занимаемые драйвером (`300`…`314`), разобраны
в [08-память-и-системная-область.md](08-память-и-системная-область.md), §8.2; описания в [Рад] и [РСП]
совпадают.

## 12.6в. Защита программ от копирования

[Рад] — единственный из проработанных источников, где приёмы защиты магнитофонных
программ разобраны системно. Приведены как способ понять поведение «неудобных» файлов,
так и объяснение того, **почему штатные средства их не берут**.

| Приём | Как работает | Как обойти |
| --- | --- | --- |
| **Разбиение файла** | Файл пишется как несколько подряд идущих файлов: первый — загрузчик, он сам читает остальные (обычно через `EMT 36` с собственным блоком параметров) | Читать по частям, разбираясь в загрузчике |
| **Неудобное имя** | В имени файла используются символы, которые **невозможно ввести с клавиатуры**, — вплоть до **кода 0 между буквами**. Штатное `М`(АГНИТОФОН) такой файл найдёт (при пустом имени берётся первый встреченный), а вызвать по имени нельзя | Читать «первый попавшийся» файл; имя восстанавливать по заглавию из ячеек `332`…`351` |
| **Нечётный адрес загрузки** | Массив грузится по нечётному адресу; попытка запустить/сохранить обычными средствами даёт ошибку обращения к слову | Работать байтовыми командами; при перезаписи выравнивать адрес |
| **Адрес загрузки ≤ `730`** | Массив накрывает **векторы прерываний** системной области → **автозапуск** без явной команды `С`(ТАРТ) | См. [08-память-и-системная-область.md](08-память-и-системная-область.md), §8.3 |
| **Подмена вектора `4`** | В вектор ошибки обращения к памяти (`4`) заносится адрес перезапуска, либо код `2` (`RTI`), либо адрес `100000` — при срабатывании программа стирается или машина уходит в монитор | Перед разбором подставить в вектор `4` собственный обработчик |

> Автор подчёркивает: все перечисленные приёмы **не мешают чтению файла как массива
> данных** — они мешают только штатным командам монитора. Регенерация (восстановление
> работоспособной копии) сводится к чтению массива фиктивным чтением, разбору заглавия
> и повторной записи с исправленными заглавием и адресом.

## 12.7. Инструменты в этом архиве

Для подготовки WAV-файлов, воспроизводимых на реальный БК через магнитофонный вход,
в архиве есть три независимых конвертера `.bin` → `.wav`:

| Каталог | Реализация |
| --- | --- |
| `bin2wav/` | Node.js CLI (`npm install -g bin2wav-cli`); ключи `--input/--output/--model 11/--speed/--play` |
| `bkbin2wav/` | Python (`bkbin2wav.py`) и Go (`gobkbin2wav/`) |
| `bk-wav/`, `bkwav/` | Исходники на C: `bkbin2wav`, `bin2bk`, библиотека `wavlib/` |

Ключ `--model 11` в `bin2wav` даёт запись на 17 % быстрее, пригодную для БК-0011(М),
но несовместимую с БК-0010(-01).

Эмулятор `bkemu-QT` читает и пишет WAV-образы ленты напрямую
(`devemu/Tape.cpp`, окно «Магнитофон»).
